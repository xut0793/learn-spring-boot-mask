## 1.1 一个例子讲透：为什么不是简单 `replace`

需求听起来简单到不需要讨论：

> 用户列表接口返回的手机号，中间四位要变成星号。`13812345678` → `138****5678`

如果现在让你写，你大概会写出这样一行：

```java
String masked = phone.replace(phone.substring(3, 7), "****");
```

跑一下 `13812345678`，输出 `138****5678`，完美。提交、上线。

### 第一个 bug：`replace` 替换的是**所有**匹配

三天后测试提了个单子，某个用户的手机号显示成了 `138********`（11 个字符，但中间有 8 颗星）。

我们来算一下这个手机号是 `13812341234`：

| 步骤 | 结果 |
| --- | --- |
| `phone.substring(3, 7)` | `"1234"` |
| `phone.replace("1234", "****")` | 字符串里有**两处** `1234`（下标 3 和下标 7），都被替换 |
| 最终输出 | `138` + `****` + `****` = `138********` |

`String.replace(CharSequence, CharSequence)` 的语义是「替换全部出现」，而我们想要的是「替换指定位置」。这两件事只是在大部分测试数据上碰巧结果一样。

修一下，改成按位置拼接：

```java
String masked = phone.substring(0, 3) + "****" + phone.substring(7);
```

### 第二个 bug：不是所有输入都长成手机号的样子

```java
mask(null);            // NullPointerException
mask("");              // StringIndexOutOfBoundsException
mask("138");           // StringIndexOutOfBoundsException
mask("未填写");         // StringIndexOutOfBoundsException
mask("+8613812345678"); // 输出 "+86****3812345678"，前缀被当成号码切了
```

生产数据永远比你想象的脏。历史遗留的空字符串、用户填的「保密」、运营导入的国际号码，全都会撞上这段代码。

### 第三个 bug：手机号只是开始

产品接着说：身份证也要脱敏，保留前 6 后 4；银行卡保留前 4 后 4；邮箱只保留第一个字符，`@` 后面的域名要留着；地址要遮住门牌号。

于是代码变成这样：

```java
if ("phone".equals(type)) {
    return raw.substring(0, 3) + "****" + raw.substring(7);
} else if ("idCard".equals(type)) {
    return raw.substring(0, 6) + "********" + raw.substring(14);
} else if ("bankCard".equals(type)) {
    // 银行卡 16~19 位不定长，星号数量得算，不能写死
    ...
} else if ("email".equals(type)) {
    // 得先找 @ 的位置
    ...
}
```

每加一种类型，这个方法就长一截；每个分支里都要重复处理空值和长度校验；星号数量在不定长字段上还得现算。这段代码会以肉眼可见的速度腐烂。**第 4 章会用策略模式把它彻底拆掉。**

### 第四个 bug：规则会变，而且是线上突然要变

安全部门发来通知：身份证不能只遮 8 位，中间必须全遮，只留前 1 后 1。

如果规则写死在代码里，这意味着**改代码 → 提测 → 发版**。而合规整改往往要求当天生效。**第 7 章会把规则做成配置，并支持不重启热更新。**

### 第五个 bug：不是所有人都该看到星号

客服接到用户来电，需要核对手机号后确认身份，但客服后台显示的是 `138****5678`，没法核对。于是有人提议「给客服开个白名单接口返回明文」——然后这个接口就成了整个系统最大的漏洞。

**同一份数据，对不同角色应该有不同的可见度。** 这不是加个 `if (isCustomerService)` 就能解决的，涉及角色从哪来、怎么审计、可逆还原怎么做。**第 5 章讲角色，第 14 章讲可逆还原。**

### 小结

「把手机号中间四位改成星号」这句话背后藏着五个问题：**位置精确性、输入健壮性、类型可扩展性、规则可配置性、权限差异性**。一个能上生产的脱敏方案，要同时回答这五个问题。这就是为什么本项目最终有 38 个类，而不是一个工具方法。

## 1.2 脱敏 ≠ 加密 ≠ 哈希

这三个词经常被混着用，但它们解决的是完全不同的问题。区分清楚是理解后面所有内容的基础。

| | 数据脱敏 | 加密 | 哈希 |
| --- | --- | --- | --- |
| 典型输出 | `138****5678` | `k3Jd9fLm2Xp...` | `a8f5f167f44f...` |
| 能还原吗 | 一般不能（除专门设计的可逆脱敏） | 能，有密钥就能 | 永远不能 |
| 输出还看得懂吗 | **看得懂**，保留了格式和部分信息 | 看不懂，变成乱码 | 看不懂，定长摘要 |
| 主要用途 | 给人看：界面展示、日志、报表 | 给机器存/传：数据库字段、网络传输 | 校验：密码验证、数据完整性 |
| 典型算法 | 替换、截断、掩码 | AES、RSA | SHA-256、bcrypt |

关键差别在**「输出还看得懂吗」**这一行。

脱敏的核心价值恰恰在于「保留了部分信息」：`138****5678` 让客服能确认这是用户本人的号（前 3 后 4 对得上），让运营能看出这是移动号段，让开发能在日志里定位到具体用户——但拿到这串字符的人没法给这个号码打电话。这叫**保持业务可用性的前提下降低敏感度**。

而加密后的 `k3Jd9fLm2Xp...` 展示在界面上毫无意义，用户看不懂，客服也没法核对。哈希更是连长度特征都没了。

所以：

- 用户密码 → **哈希**（bcrypt），你永远不需要知道用户的原始密码
- 数据库里的身份证号 → **加密**存储（如果安全要求高），或明文存储 + 严格权限控制
- 接口返回给前端的身份证号 → **脱敏**
- 日志里打印的身份证号 → **脱敏**

本项目做的是最后两件事。

> **一个常见的误区**
> 有人会说「我把手机号 AES 加密后返回给前端，前端解密显示，这样安全」。这是自欺欺人——密钥必须下发到前端，抓个包就拿到了。脱敏之所以有效，是因为**被遮掉的信息根本没有离开服务器**。

## 1.3 为什么必须做

### 合规不是可选项

中国大陆现行的三部主要法律都对个人信息处理提出了明确的技术要求：

| 法律 | 生效时间 | 与脱敏相关的要求 |
| --- | --- | --- |
| 《网络安全法》 | 2017-06 | 网络运营者应采取技术措施防止信息泄露、毁损、丢失 |
| 《数据安全法》 | 2021-09 | 开展数据处理活动应建立全流程数据安全管理制度，采取相应技术措施 |
| 《个人信息保护法》 | 2021-11 | 处理个人信息应采取加密、去标识化等安全技术措施；最小必要原则 |

《个人信息保护法》里的「去标识化」**基本就是在说脱敏。而**「最小必要」原则的工程含义是：一个角色只应该看到完成其工作所必需的最少信息。客服核对身份需要前 3 后 4，那就只给前 3 后 4。

行业规范里还有更具体的：支付卡行业的 PCI DSS 明确规定卡号展示时最多只能显示前 6 后 4 位。

### 泄露的代价是真实的

IBM 每年发布的《数据泄露成本报告》里，单次数据泄露事件的平均成本长期处在数百万美元量级，且逐年上升。但对多数团队来说，更现实的代价是：

- 一次事故导致的紧急停服和整改
- 监管约谈、通报、下架
- 用户信任的流失（这个最难量化也最难挽回）

### 大部分泄露发生在「意想不到的地方」

真正被攻破数据库的案例其实是少数。更常见的泄露路径是这些：

- **日志**。`log.info("用户信息: {}", user)` 一行代码，把整个对象的 `toString()` 写进了日志文件，而日志文件被同步到了全公司都能查的日志平台。这是本项目专门用第 10 章讲 Logback 通道的原因。
- **接口冗余字段**。前端只需要显示用户名，后端图省事直接返回整个 `UserEntity`，身份证和银行卡就在响应报文里，F12 一按就能看到。
- **测试环境**。生产库直接 dump 一份导入测试环境，外包同学的电脑上就有了几百万条真实用户数据。
- **数据导出**。运营导出的 Excel 报表，在微信群里传了一圈。

脱敏的价值就是：**即使发生了上面这些事，泄露出去的也是 `138****5678`。**

## 1.4 静态脱敏 vs 动态脱敏

这是脱敏方案的第一个分岔路口，选错了后面全是坑。

### 静态脱敏（SDM，Static Data Masking）

**数据在落盘前就已经被改写，存储里保存的就是脱敏后的值。**

```
用户输入 13812345678  →  脱敏  →  数据库里存的是 138****5678
```

- 典型场景：生产库同步到测试环境时批量脱敏；密码哈希后存储
- 优点：一劳永逸，数据库层面就没有明文，DBA 也看不到
- 缺点：**明文永久丢失**。以后业务要给用户发短信怎么办？要核对身份怎么办？要对接第三方实名认证怎么办？全都没法做了

### 动态脱敏（DDM，Dynamic Data Masking）

**存储里仍是明文，只在数据「离开系统」的那一刻按当前访问者的权限打码。**

```
数据库里存 13812345678
   ├─ USER 请求接口   →  出口打码  →  138****5678
   ├─ ADMIN 请求接口  →  旁路      →  13812345678
   └─ 写日志          →  出口打码  →  138****5678
```

- 优点：明文保留，业务功能不受影响；同一份数据可以对不同角色呈现不同结果；规则可以随时调整，不需要刷数据
- 缺点：明文还在库里，所以**数据库本身的访问控制必须做好**；每次访问都要计算，有性能开销

### 本项目为什么选动态

三个理由：

1. **业务需要明文。** 发短信、实名核验、客服核对身份，这些功能都要原始数据。静态脱敏一旦落地就没有回头路。
2. **角色差异化是硬需求。** 静态脱敏做不到「ADMIN 看明文、USER 看星号」——数据只有一份，而且已经被改了。
3. **规则会变。** 动态脱敏改配置就生效（第 7 章的热更新）；静态脱敏改规则得重新刷全表数据，而且原始数据早就没了，根本刷不回来。

代价是要接受两件事：库里有明文（所以要管好数据库权限），以及运行时有计算开销（所以有第 8 章的缓存和第 16 章的压测）。

> **提前给你一个心理准备**
> 动态脱敏最反直觉的一点是：本项目的四个切入点里，有两个（AOP 和 MyBatis）会**真的修改内存里的 Java 对象**，让应用层再也拿不到明文。这等于把动态脱敏做出了一部分静态脱敏的效果，也带来了一整类 bug。这是第 2 章的核心内容，也是整份教程最重要的心智模型。

## 1.5 五种常用脱敏算法

知道有哪些手段，才能在需求来的时候选对工具。

### 1. 替换 / 掩码

用固定字符替换一部分内容。这是最常用的一种，本项目的四个内置策略全都属于这一类。

```
13812345678         → 138****5678
110101199003078515  → 110101********8515
6222021234567890723 → 6222***********0723
```

特点：保留长度和格式特征，不可逆，性能极好（就是字符串拼接）。

### 2. 截断

直接砍掉一部分，不补占位符。

```
13812345678  → 138
北京市朝阳区某某路 88 号  → 北京市朝阳区
```

特点：输出变短，会丢失长度特征。适合只需要粗粒度信息的场景，比如统计用户所在城市。

### 3. 加密

用可逆算法处理，持有密钥的人能还原。

```
13812345678  →  Base64(IV + AES-GCM 密文)
```

特点：**可逆**。本项目第 14 章用 AES-GCM 实现「客服验证身份后可查看完整手机号」。注意加密结果不适合直接展示给用户看（回顾 1.2 的对比表）。

### 4. 混淆 / 假名化

替换成格式合法但完全虚假的数据。

```
张三 → 李四
13812345678 → 13900000001
```

特点：输出看起来像真的，因此**特别适合测试环境**——测试同学能正常跑业务流程，但数据全是假的。缺点是需要维护映射关系才能保证一致性（同一个用户每次都要混淆成同一个假名，否则关联查询就崩了）。

### 5. 泛化 / 区间化

把精确值替换成范围。

```
生日 1990-03-07  →  1990 年代
年龄 28          →  25~30
薪资 23500       →  2~3 万
```

特点：常用于数据分析和统计场景——保留了分析价值，但无法定位到个人。

### 本项目用了哪些

| 算法 | 项目里的落地 | 对应章节 |
| --- | --- | --- |
| 替换 / 掩码 | 手机、身份证、银行卡、邮箱、地址、快递单号策略 | 第 4 章 |
| 加密 | AES-GCM 可逆还原 | 第 14 章 |
| 截断、混淆、泛化 | 未实现，但可通过实现策略接口扩展 | 第 4 章练习 |

## 1.6 一个好的脱敏方案要满足什么

这一节是全书的验收标准。往后每一章你都可以回来对照，看看这一章解决了哪一条。

### 不可逆性

展示用的脱敏结果不能被反推回原文。看起来简单，但有个容易忽略的陷阱：**如果保留的信息太多，脱敏就是假的**。

比如身份证保留前 6 后 4：前 6 位是行政区划码（公开信息），后 4 位含校验位。中间被遮的 8 位是「出生年月日」——如果攻击者本来就知道这个人的生日，那整个身份证号就被还原了。这类攻击叫**关联推断**。

所以保留位数不是拍脑袋定的，需要评估。这也是为什么规则要可配置（第 7 章）——安全评估的结论变了，配置跟着改就行。

### 业务一致性

脱敏后的数据要保持原有格式和业务特征。手机号脱敏后还得是 11 个字符，邮箱脱敏后还得有 `@` 和域名，日期字段绝对不能被打成星号（会破坏 JSON 类型，前端解析直接报错）。

这条派生出一个重要约定：**日期和数字类型默认不脱敏**（`plan.md` 明确写了）。第 17 章会讲为什么，以及确实需要处理时该怎么做。

### 低侵入

业务代码只声明「这个字段是敏感数据」，不应该出现任何打码逻辑。

理想形态就是本项目的样子——业务代码里只有一个注解：

```java
@Sensitive(type = SensitiveType.PHONE)
private String phone;
```

至于用什么规则、当前用户是什么角色、要不要走缓存、打点到哪个指标，业务代码完全不需要知道。

### 高性能

脱敏在**每一次响应的每一个敏感字段**上都会执行。一个返回 100 条记录、每条 5 个敏感字段的列表接口，一次请求就是 500 次脱敏调用。

本项目的应对：Caffeine 缓存（第 8 章）+ 按通道开关跳过不需要的路径（第 13 章）+ 压测验证（第 16 章）。

### 可控性

- 按角色控制可见度（第 5 章）
- 规则外部化、可热更新（第 7 章）
- 可观测：调用量、耗时、失败数、旁路比例（第 8 章）

最后一条容易被忽略但很关键：**如果你不知道脱敏被调用了多少次、失败了多少次，你就不知道它到底在不在工作。**

### 可扩展

新增一种脱敏类型，不应该修改框架代码。本项目的做法是实现策略接口 + 注册为 Spring Bean，连枚举都不用改——第 4 章会用「快递单号」这个真实需求演示一遍。

## 本章小结

- 「手机号中间四位打星」背后有五个真问题：位置精确性、输入健壮性、类型可扩展性、规则可配置性、权限差异性
- 脱敏、加密、哈希解决不同问题，关键区别是**输出还能不能看懂**；脱敏的价值在于保留部分可用信息
- 合规（尤其《个人信息保护法》的去标识化与最小必要）让脱敏成为必选项；而多数泄露发生在日志、冗余字段、测试环境、数据导出这些「意想不到的地方」
- 本项目选**动态脱敏**：库里存明文，出口按角色打码。代价是要管好数据库权限、要处理运行时开销
- 六条验收标准：不可逆、业务一致、低侵入、高性能、可控、可扩展

下一章我们会把 Spring Boot 的数据流画出来，找到四个可以「下手」的位置，并建立整份教程最重要的心智模型：**出口通道 vs 突变通道**。

## 课后练习

**练习 1.1** 下面这段代码想脱敏邮箱，保留第一个字符和整个域名。它有两个 bug，找出来并说明触发条件。

```java
public String maskEmail(String email) {
    int at = email.indexOf("@");
    return email.charAt(0) + "*".repeat(at - 1) + email.substring(at);
}
```

**练习 1.2** 某系统把用户手机号做 SHA-256 哈希后存库，界面上展示哈希值的前 8 位。产品说「这样又安全又能区分用户」。请指出这个方案的两个致命问题。

**练习 1.3** 下面四个场景，各自应该用静态脱敏还是动态脱敏？为什么？

1. 把生产数据库导入外包团队的测试环境
2. 用户在 App 个人中心看自己的银行卡号
3. 用户密码
4. 客服后台展示用户手机号，且客服核对身份后需要看到完整号码

## 练习答案

### 练习 1.1

**Bug 1：`email` 里没有 `@` 时崩溃。**
`indexOf` 返回 `-1`，于是 `"*".repeat(-1 - 1)` 抛 `IllegalArgumentException`（`repeat` 不接受负数）。触发条件：脏数据，比如用户填了 `不便告知`，或者字段存的是空字符串（`charAt(0)` 先抛 `StringIndexOutOfBoundsException`）。

**Bug 2：`@` 在第一个字符时星号数量算错。**
输入 `@example.com`，`at = 0`，`repeat(-1)` 同样抛异常。即使把 `repeat` 换成安全实现，`charAt(0)` 拿到的是 `@` 本身，输出会变成 `@@example.com`，逻辑上也是错的。

另外还有一个空指针问题：`email` 为 `null` 时 `indexOf` 直接 NPE。

对比一下项目里的实现（`mask-starter/src/main/java/com/learn/mask/strategy/EmailMaskStrategy.java`），它用 `at <= 0` 一次挡掉了「没有 `@`」和「`@` 在开头」两种情况，并且回落到通用的保留前后缀逻辑，而不是抛异常：

```java
int at = raw.indexOf('@');
if (at <= 0) {
    return MaskUtils.keepMask(raw, rule);
}
```

### 练习 1.2

**问题 1：哈希不可逆，明文永久丢失。** 系统再也没法给用户发短信、做实名核验、让客服核对身份。这实际上是把动态脱敏需求错误地用静态方案实现了。

**问题 2：手机号的哈希可以被暴力破解。** 中国大陆手机号的空间只有约 11 位数字里的有限号段组合，量级在 10 亿级别。用一台普通机器把所有可能的手机号跑一遍 SHA-256 建成彩虹表，是几个小时的事。**哈希只对高熵输入（比如强密码）有保护作用，对手机号、身份证号这种低熵、格式固定的数据基本等于没加密。**（这也是为什么密码哈希要用 bcrypt / Argon2 加盐并且故意设计得很慢。）

附带问题：只展示哈希前 8 位会有碰撞，不同用户可能显示成同一串，「区分用户」这个目标也没达成。

### 练习 1.3

| 场景 | 选择 | 理由 |
| --- | --- | --- |
| 1. 生产库导入外包测试环境 | **静态脱敏**（配合混淆） | 数据一旦离开生产环境就不受控，必须在导出时就永久改写。这里还应该用混淆而不是打星，否则测试同学没法跑通业务流程 |
| 2. 用户看自己的银行卡号 | **动态脱敏** | 明文必须保留（支付要用），只在展示时打码。注意这里角色是「数据主体本人」，按业务需要可以放宽到显示后 4 位 |
| 3. 用户密码 | **都不是，用哈希** | 密码是唯一一种「系统永远不需要知道原文」的数据。用 bcrypt / Argon2 加盐哈希，既不是脱敏也不是加密 |
| 4. 客服后台手机号，验证后可看完整 | **动态脱敏 + 可逆还原** | 默认展示打码值，通过独立的还原接口按角色放行明文。这正是本项目第 14 章的设计，注意关键点是「还原走独立接口并留审计」，而不是「给客服的接口直接返回明文」 |
